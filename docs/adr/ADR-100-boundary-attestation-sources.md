# ADR-100: Boundary attestation derives from hydration manifest + proxy log + launch records — retro-fitted record

- **Status:** Proposed
- **Date:** 2026-10-04
- **Ticket:** CAP.3
- **Requirement ids:** REQ-ARCH-20
- **Spec:** §12.4 (amended)

## Context

REQ-ARCH-20's original wording made the audit's own pipeline the primary attestation source for
boundary integrity. The amendment restated the sources: the hydration manifest + the proxy log +
sub-agent launch records ARE the attestation, with the audit machinery secondary. The matrix
records MET-DIFFERENTLY without an ADR; this retro-fits the record.

## Decision

Boundary attestation is grounded in the three operational records (manifest, proxy log, launch
records) that `packages/mirror/src/attestation.ts` persists per run — these are generated by the
system doing the work, not reconstructed by a later audit. The audit pass compares/flags; it is
not the source of truth.

## Consequences

- Attestation survives an audit outage — the records exist because the run happened.
- CAP.3's launch-ledger cap enforcement (ADR-094) extends this: `subagent_launches` is also the
  iteration-cap ledger, so the attestation table now carries control, not just evidence.

## Alternatives considered

- Audit-first attestation: circular — the audit can't attest what it never observed.

## Revisit trigger

Reopen if a run shape bypasses the hydration/launch pipeline (attestation would go blind), or if
the records' retention/writability guarantees weaken.
