The high level goal of this session is to do the deep research and careful product, UI, systems, and software design work needed to turn the toy project at ~/agent-discourse repo into a production-grade, consumer-ready monetizable web platform for AI-assisted writing projects. The bare bones MVP can focus on the academic niche as this is what the existing editorial-review agent skill is tailored to, but ideally we want to support all possible use cases (high academia, journalism, blog, creative writing, business writing, perhaps other genres). Essentially, I want to translate what is currently expressed as ad hoc locally-executed agent skills that write structured markdown files representing agent, reviewer, and shared memory structures into a beautiful, well-designed, delightful consumer-facing web platform for doing AI-assisted writing. For UI/UX inspiration, I have in mind the design styles used by current leading coding agent harnesses/IDEs like Cursor, Devin Desktop, Codex, and so on -- but our harness will be designed specifically for the written word, not code. Essentially, I want to design an agentic discourse harness and IDE that does for the drafting, research, and editorial process of written prose generation what the leading agent harnesses/IDEs do for code. There should be a beautiful landing page on par with those used for leading frontier AI consumer products, users should be able to create an account and access a limited trial version of the web IDE and then, exactly analogous to how it's done with Claude Code, Devin Desktop, Cursor, Codex, etc., have the ability to subscribe to different usage tiers, connect billing, and so on. I want you to really deeply and carefully research and study the user experience of the existing leading coding agent IDEs and reason carefully about how its functionality and user experience might map onto this novel product surface (e.g., billing and usage tracking dashboards would be one example, but I want you to reason about all core UI/UX functionality). It is very important that we get the UI/UX of the web experience absolutely perfect; it must rival the leading coding agent providers in terms of feature richness, intuitiveness, general elegance/beauty, and simplicity. As for the actual product and its features, I want you to proactively reason about the details here, using the functionality of the ~/agent-discourse repo as a starting point, and I want you to think, research, and reason very critically and deeply about what the optimal feature set might look like, given all of our constraints so far. For now, I will fill in some hard requirements myself, but I want to emphasize that you are expected to evaluate these critically and to creatively and proactively fill in missing details, refactor the design optimally, and think of additional or missing features yourself as you synthesize a final design. At the highest level, this platform is about producing artifacts of written prose, so there should obviously be a straightforward way to manage writing 'projects' -- create, re-organize, open for editing, etc. Users should be able to open a project for editing in the discourse harness IDE and pick up work on it. For a brand new project, users may start from scratch, upload an outline, or upload a first draft. If starting from scratch, users should be able to have long-context chats with an agent able to do web research natively, in other words, users should essentially have the ability to run a fully-fledged ChatGPT or Claude session from the IDE itself (we'll need to think carefully about the implementation details, as we'd probably prefer to reuse an existing agent harness capable of ChatGPT-level deep research rather than hand-roll). And anyway, the user should at some point be able to generate from that session an official 'outline' doc. If the user has generated an outline in-app or uploaded one, then the next phase is to actually generate the v1 draft from the outline, for which there is an existing skill in ~/agent-discourse to be ported over to the new system. And then from there, whether a user generated a draft in-app from an outline upstream or uploaded their own first draft, the next stage is to do an editorial-review pass (in the academic case) and perhaps we offer different versions of editorial-review protocol for different genres (academic, journalism, business, creative writing, blog, marketing, etc.). Whether users are generating a draft from an outline or running the editorial-review step, the respond-to-review step, or something else, the app should have some clear and intuitive way of representing the state of the project and these ongoing processes live in the UI, and on the backend we will need to think very carefully about the optimal system architecture to facilitate this. As the user operates the system, the web IDE should also have a beautiful, intuitive, and robust system for making all of the intermediate artifacts available for inspection and editing by the user. We need to think extremely carefully and critically about which artifacts should be transparently surfaced and inspectable/editable by the user via the UI, how precisely to do this in the most optimal UI/UX, and even more importantly, whether there is a subset of these artifacts and project memory that should actually be hidden from the user and only visible from the harness's perspective, and if so, precisely which, and why -- whether it's to maximize simplicity and user experience, or to hide the secret sauce powering our platform, or likely both. We should also think very carefully about the data model and the system architecture powering the project authoring experience. So far in ~/agent-discourse we have a notion of an 'author' agent with its own agent-isolated memory that only it can access, a 'review' agent with its own independent memory, shared memory, and so on. It's likely that this will generalize into a generic notion of an agent-type, each keeping track of its own unique memory, and perhaps other agentic configurations like specialized agent toolsets, additional knowledge bases, available skills, and things like that, perhaps also model and other configurations. We may even want users to be able to track for each agent within a given project what its overall spend has been, and on what, with options to dig into run history and understand cost/latency of past actions done with such and such configs, though we want to be very careful not to over-expose detail here to end users. It's also an open question exactly what the optimal UI/UX looks like when it comes to representing these separate agent roles in the IDE itself, if this even makes sense to begin with, so I want you to reason very carefully and critically, from first principles, about that as well. Additionally, unlike a code editor, the doc viewer and editor within the IDE should probably be formatted markdown, i.e., markdown on the backend but formatted and formattable via a beautiful formatted editor UI (likely there is existing tooling available so that we can avoid rebuilding this from scratch; you'll want to do careful research to understand our options and reason carefully about which is the best fit for our use case, optimizing for beauty/simplicity/elegance). Another problem we need to think about is whether we want the MVP to run the skills from ~/agent-discourse in a pre-existing generalized agent harness with deep research and other capabilities like Claude Code, ChatGPT, etc., or hand-roll a harness from scratch. My intuition tells me that we may want to simply do execution on a prebuilt mature harness, to start, since much of the power of the harness comes from the deep research and other capabilities of, e.g., Claude Code, which is what I've been using to run ~/agent-discourse projects manually -- but you should do some careful research into what our options are here and what makes the most sense. Additionally, I wonder if users should be able to interact with the project via a text interface that itself just wraps Claude or similar plus a couple of extra tools for triggering workflow/skill passes from the different agent-types; but again, we need to think very carefully and critically about what the optimal design here is. For the absolute most bare bones MVP, it may be enough to only expose the IDE, artifact browser and editor, and agent-types, and effectively only allow users to run the next workflow in the sequence (if there's an outline but no drafts, the draft-from-outline workflow; if there's a draft but no review, the editorial-review one, if there's an outstanding review dossier but no follow-up draft, the respond-to-review workflow, and so on). But this would be far too impoverished an experience for the consumer AI user of 2026, so we need to think very carefully about how to give this platform a UI/UX that feels as powerful as the most frontier coding agent IDEs, and I want you to research this rigorously and creatively and proactively incorporate your own ideas and product and design judgements. Additionally, users should have the ability to manage their 'personas' analogous to how personas are handled in ~/agent-discourse; this part is tricky because the persona definition and/or the writing samples may get out of sync with the output of the actual persona generation workflow which is quite expensive to run, so we may need to think very carefully about how to indicate this to the user and make the user experience around persona editing/generation/refreshment as seamless and simple and intuitive as possible. Users should also be able to upload writing samples from a diverse range of file formats directly, as well as link to existing articles on the web, a Substack, Medium, or perhaps others, and all of these uploaded/linked writing samples should be transformed into and persisted as markdown in a consistent way, and for cases like a linked SubStack, Medium account, or something else, the user should be able to omit specific articles, re-sync with linked source, and so on. Users should also have the option to draft their own custom persona description, or not, and have all of this context feed into a run of the generate-persona workflow with a straightforward analogue in ~/agent-discourse. These workflow runs should be modeled on the backend and from a UI/UX standpoint in a way consistent with the others inside the IDE, and again, we need to think carefully about how to keep track of drift in the persona description or article samples and the most recently generated persona scaffolding. And, of course, the user should be able to link a persona to a project and perhaps the projects should by default also be organized by persona, though the default location for new projects should be the persona-less case. We should also think carefully about whether users should be able to change a project's persona, and I think for the MVP, we perhaps should just not allow this to change after the first draft is generated, but you should do some research and think critically and use your best judgement here on what the optimal UI/UX around this should be. And, of course, the IDE should auto-save progress in the background in such a way that users almost never experience data loss from refreshes or the like, consistent with the way other frontier coding agent harness IDEs and live editing tools work.
