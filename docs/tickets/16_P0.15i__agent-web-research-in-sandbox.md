## The problem (diagnosed live, P0.15h Stage B, 2026-09-09)

The full Review runs green through the letter and the harness takes the **deliver** path, but
`runDeliveryTransaction` throws `DeliveryValidationError("cited_not_fetched")`
(`packages/mirror/src/delivery.ts` — `validateCitedFetched(claims, fetchedNormalizedUrls)`): every claim that
cites a URL is a "miss" because `fetch_log` for the run holds **only `kind='inference'` rows** — zero
`fetch`/`search` rows. Root cause chain:

1. **The model never invokes a server-side web tool.** `usage_records.searches = 0`, `fetches = 0` across the run.
   So no `web_search_tool_result` blocks appear in any response, and no source is ever fetched.
2. **The SDK request carries no server-side web-search tool.** `packages/engine/src/options.ts` lists
   `"WebSearch"`/`"WebFetch"` only as allowed-tool NAMES (`ALLOWED_TOOLS`); nothing adds Anthropic's server-side
   web-search tool (`web_search_20250305`, an entry in the request `tools[]` array) — so the model has no working
   search tool and fact-checks from its training knowledge instead. The egress-proxy is already BUILT to expect
   the tool: `apps/egress-proxy/src/url-policy.ts` `injectUrlPolicyIntoBody` walks `body.tools[]` for
   `isServerWebTool` (name/type contains `web_search`/`web_fetch`) and scopes its `allowed_domains`/`blocked_domains`
   — but there is no such tool in the request to scope.
3. **Client-side `WebFetch` can't reach the internet anyway.** The pod's network is locked to the egress-proxy
   (api.anthropic.com only), so a client-side fetch of an arbitrary source URL has no route. Server-side web_search
   does NOT need pod egress — Anthropic performs the fetch inside the `/v1/messages` call the proxy already allows.

**Already landed in P0.15h (do NOT redo):** the egress-proxy now PARSES `web_search_tool_result` /
`web_fetch_tool_result` response blocks and logs a `fetch` row per returned page URL
(`apps/egress-proxy/src/outbound-limits.ts` `collectResultUrls` + `extractResponseServerToolsSse`, commit
`f242ab8`) — so the moment the model actually does server-side web_search, the source URLs land in `fetch_log`
and `cited⇒fetched` has real provenance. The remaining gap is purely ENABLING the tool in the request (this
ticket).

## Key architectural finding (research, P0.15h close — informs the whole design)

The vendored `@anthropic-ai/claude-agent-sdk` (`apps/run-task/vendor/claude-agent-sdk`) is a **thin wrapper that
spawns the native `claude` CLI binary** (`sdk.mjs` → `pathToClaudeCodeExecutable`); the actual `/v1/messages`
request `tools[]` array — where an Anthropic server-side web-search tool lives — is assembled **inside the
compiled binary, which is NOT in-tree** and can't be inspected here. Grepping the vendored `.mjs`/`.d.ts` for
`web_search_20250305`, `max_uses`, `allowed_domains`, `betas` → zero hits; `WebSearch` appears only as a
permission-rule name + a usage counter. So in standard Claude Code, enabling the `WebSearch` allowed-tool is what
makes the CLI add the server tool — but that step is opaque, and **Rhema currently relies on it implicitly and it
is not happening** (`searches=0`). Corroborating seams:
- Engine passes only NAMES: `packages/engine/src/options.ts:26-37` (`ALLOWED_TOOLS`) + `:112-138`
  (`buildQueryOptions` returns no `additionalModelRequestFields` / `extraArgs` / `betas` / web-tool entry). The
  SDK Options type *does* expose `extraArgs?` (`sdk.d.ts:1542`) and `betas?` (`sdk.d.ts:1581`) — unused.
- Proxy ASSUMES the tool is already present: `apps/egress-proxy/src/url-policy.ts:33-64` `injectUrlPolicyIntoBody`
  returns the body unchanged when `body.tools` is not an array (`:42-43`) and only rewrites existing web tools —
  it never ADDS one. `outbound-limits.ts:9-10` states the server-tool-side design intent explicitly.
- `WebSearch` = server-side (metered via `server_tool_use.web_search_requests`, `packages/engine/src/usage.ts:18`);
  `WebFetch` = client-side in classic Claude Code (a real HTTP fetch, `sdk-tools.d.ts:3592-3616`) — impossible in
  the sandbox. But Rhema's proxy treats BOTH as server tools (`url-policy.ts:16`, `outbound-limits.ts:42-44`) — a
  client-vs-server mismatch to resolve.

## What to build (Stage A — offline construction)

Research + design carefully; the three concrete approaches (choose after verifying the native-binary behavior),
smallest first:

1. **Verify/repair the native-CLI path.** Confirm `claudeCodeExecutablePath` is wired (`options.ts:107-108,123`,
   `agent-sdk-engine.ts:33-34,60`) and that the vendored `claude` binary version actually emits the Anthropic
   server-side `web_search` tool when `WebSearch` is allowed. Reproduce against `dev` (or a captured request) and
   inspect whether `body.tools[]` carries a `web_search` entry. If the binary is missing/old/gated, that alone is
   the bug.
2. **Pass the server tool / beta explicitly through the SDK.** If the binary won't add it, add `extraArgs`
   (`sdk.d.ts:1542`) and/or `betas` (`sdk.d.ts:1581`, e.g. the web-search beta) — or an
   `additionalModelRequestFields`-style `tools:[{type:"web_search_20250305",name:"web_search",max_uses:N}]`
   passthrough — to `AgentSdkQueryOptions` (`options.ts:55-89`) + set them in `buildQueryOptions` (`:112-138`).
3. **Make the proxy the guarantor (most robust — the proxy already owns the web-tool body).** Change
   `injectUrlPolicyIntoBody` (`url-policy.ts:33-64`) from rewrite-only to **add-or-rewrite**: when `body.tools`
   has no server web tool, inject the `web_search` (server) tool scoped to the run's `ProxyUrlPolicy` domains
   (and handle the `tools`-not-an-array case at `:42-43`). Then every request carries a domain-scoped server
   web_search regardless of the CLI, aligning with the proxy being the run's single meter of record.
4. **Resolve the WebFetch client-vs-server ambiguity.** Decide whether to enable the server-side `web_fetch` tool
   too, and whether to DISABLE the client-side `WebFetch` allowed-tool (which can only no-op/error in the sandbox
   and wastes turns). Keep the name normalization in `packages/hooks/src/hook.ts:54-55` +
   `packages/engine/src/mapper/mapper.ts:40-45` (already handles both spellings).
5. **Domain policy + metering + logging (verify end-to-end).** Confirm `injectUrlPolicyIntoBody` scopes the
   now-present tool; the outbound novel-domain cap + suspicious-query check behave with real search traffic;
   `server_tool_use.web_search_requests`/`web_fetch_requests` meter into `usage_records.searches`/`fetches`; and
   the result-URL `fetch` rows (already landed, `collectResultUrls`, P0.15h `f242ab8`) write for buffered + SSE.
6. **Unit/Docker tests:** whichever enablement path is chosen emits/forces the server web_search tool into the
   request `tools[]` (unit-tested); the proxy scopes it (unit-tested); the response parser logs the result URLs
   (already tested); a `cited⇒fetched` unit passes when the ledger's citations match the logged result URLs and
   still FAILS for a genuinely unfetched citation (the §12.8(c) guard stays real).

## Acceptance criteria

- **AC1 (offline):** with web-search enabled, the SDK query options carry the server-side web-search tool in the
  request `tools[]` (unit-tested); the proxy scopes its domains and logs its result URLs (unit-tested, both
  buffered + SSE). No client-side tool that cannot function in the sandbox is left enabled to be silently no-op'd.
- **AC2 (offline):** a `validateCitedFetched` unit passes when the claim ledger's citations are present in the
  run's logged `fetch`/`search` result URLs, and still FAILS for a genuinely unfetched citation (the §12.8(c)
  guard is preserved, not weakened).
- **AC3 (live, Stage B):** a Review's verification phase on `dev` does real server-side web research
  (`usage_records.searches > 0`), the proxy writes `fetch_log` rows (`kind='fetch'`) with the source URLs, and the
  delivered claim ledger's citations resolve against them — `runDeliveryTransaction` no longer throws
  `cited_not_fetched`.
- **AC4 (live, Stage B — closes the milestone):** a COMPLETE green Review delivers to `completed`/delivered with a
  `correspondence_items` row, `boundary.attested violations = 0`, every sidecar `parseStatus = ok`, and
  `assessPhase0ExitForRun` green (boundary/sidecar/cited⇒fetched). This is the last construction input to
  16a_GATE-G1.
