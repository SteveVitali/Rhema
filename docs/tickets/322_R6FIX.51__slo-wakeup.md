## The diagnosis (prod, `begin read only` — tunnel :15433)

The post-ADR-116 residual was **single-run-scoped**: `01M88BF2H22NM86A5E74MS433Z` (N11's
hiccup-resumed golden op-ed, delivered 04:01Z, verified, 702 cr) produced all 487
post-deploy `detail='tail'` samples >2 000 ms — p95 4 976, max 9 795 ≈ the 10 s safety
poll. R6's `01M887YB…` and the `r6dep7-a` cohort produced none. The breach window
(03:43–04:00Z) sits exactly between the run's two `run.hiccup` events (03:41:28,
03:48:28) and delivery.

**Mechanism — wasted in-tx wakeups, not a lost bus.** `SqlEventWriter.append` publishes
the seq *inside* the still-open transaction. The woken tail pumps immediately, reads
only committed rows, sees nothing, and goes back to sleep; when the tx commits there is
no post-commit publish (ADR-116's `publishCommittedEventHighWater` covers only the ~12
terminal/transition callsites), so the batch rides the 10 s safety poll. The smoking
gun: `step.started` seq 242 (`at` 03:49:42.854 — appended by `beginStep` inside the
resume's fence+upsert+gate-sweep tx) was flushed by ~8 different subscribers spread over
03:49:48.5–52.3 — **each on its own poll schedule**, 6–9.5 s after commit. Any tx whose
commit lands >~30 ms after the append loses the wakeup→read race; the hiccup-resume
transition txs are systematically fat, which is why the residual pinned to that run.

**Ruled out:** api request latencies in the window avg 74 ms / max 436 ms (not instance
starvation); zero Redis/publish errors in api+worker logs; ~11 SSE connects/min is leg
churn (the multiplier that made the loss VISIBLE — ~8 streamers each stamped the same
late flush), not the cause.

## The fix — commit-time wakeups, one seam for every append path

Rather than adding `publishCommittedEventHighWater` to the ~17 uncovered append
callsites (fragile, and every future callsite would have to remember), the wakeup now
**defers to commit** at the writer itself:

- `packages/orchestrator/src/event-store.ts` — `beginDeferredWakes(tx)` /
  `drainDeferredWakes(bag)`: a `WeakMap<SqlClient, Map<runId, DeferredWake>>` seam.
  `SqlEventWriter.append` queues `publisher.publish(runId, seq)` into the bag when one
  is registered (one entry per run, highest seq — a 250-event batch coalesces to one
  publish), falling back to the immediate in-tx publish on runners without the seam.
- `packages/live-clients/src/tx.ts` — `PgPoolTxRunner.run` (the api AND worker binding)
  registers the bag on its `pgClientToSqlClient` wrapper and drains it **after**
  `withTenant`'s `commit` resolves. Rollback drains nothing — a publish can never
  precede its rows' visibility again.

`publishCommittedEventHighWater` stays (fresh-tx re-read still covers cross-tx
transitions); `instrumentReads` proxies `run`, not the `SqlClient`, so the WeakMap key
is stable; the PGlite test runner keeps immediate-publish semantics.
