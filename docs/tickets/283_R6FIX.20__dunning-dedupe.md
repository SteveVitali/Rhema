## Defect (verified at 277_R6LOW.1; BL-120)

`runBillingPeriodTick`'s subscription query did `join workspaces w on w.billing_account_id =
s.billing_account_id` — one row per (subscription × workspace). An account with N workspaces ran
every per-subscription arm N times: the stale `downgrade_warned_at` snapshot re-sent the 7-day
warning (and the lapse notice) once per workspace — each addressed to a DIFFERENT workspace's
owner — and inflated `warningsSent`/`pastDueLapsed`/`cancelsCompleted`. The free-tier daily
allowance query had the same join shape (its `daily:{ba}:{day}` idempotency key already deduped
the credit grant, but the fan-out still ran N `runTx` rounds). Same join class as RH-3's
auto-reload sweep (269_R6BILL.2).

## Change

Both queries now select accounts distinctly via the RH-3 convention — `join lateral` picking the
account's home workspace (`order by created_at, id limit 1`) for the tx scope, audit row, and
owner lateral. One row per subscription / per free account; all downstream behavior unchanged
(each arm was already keyed on `s.id` / `b.id`). Accounts with zero workspaces keep the prior
inner-join semantics (no row).
