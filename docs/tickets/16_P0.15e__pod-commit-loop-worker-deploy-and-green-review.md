## In scope — Stage A (offline, no spend; ends in a reviewable PR; one implement-spec session)
1. **The pod→server commit/deliver loop (D-P0.15d-4 — the load-bearing item).** Drive the run to completion
   from the pod. **Design (recommended):** the **harness drives the loop** (it holds the run token + reads
   `/work`), reusing the orchestrator's PURE completion oracle rather than re-implementing it — this keeps the
   SDK execution in the pod (the two-uid model) and the attestation on server-side facts (the harness only
   reports facts; the server's `commit` route is the durable transition). Concretely, after `runAgentPhase`
   runs a phase (`agent-entry`):
   - **Harvest + read facts:** read the committed `.rhema/phase-result.json` + the phase's produced artifacts
     from `/work` (the produced-version-ids + the predicate facts `evaluateOracle` needs). Reuse
     `@rhema/mirror` `harvest` for the produced versions and a small facts reader for the oracle inputs.
   - **Evaluate the oracle + decide next:** call `evaluateOracle`/`createFactsEvaluator` (pure, imported from
     `@rhema/orchestrator`) on `{sdkSubtype, phaseResult, predicates}` → complete / blocked / replan /
     incomplete; on a re-runnable incomplete class, re-run the phase ONCE with guidance (mirror `runPhase`).
   - **Commit + advance:** `POST /internal/runs/:id/steps/:key/commit` with the token (produced-version-ids +
     reconciled credits + the `next` decision: advance / gate / finalize). On **advance**, re-fetch the run
     spec for the next phase (`GET .../runspec`, which now returns the next uncommitted phase) + re-run
     `agent-entry`; loop. On a **gate**, commit-with-gate + exit the pod (the worker resumes later). On the
     **final** phase, assemble the `DeliveryArgs` dossier from `/work` + `POST /internal/runs/:id/deliver`.
   - **Reconcile `harness-main.ts`** to run this loop instead of forwarding-then-exiting; keep the event
     forwarding (the loop still streams each phase's events). NO secret leaves the harness (REQ-SPEC-10/11).
   - **Wire the P0.15d follow-ups into the now-live loop:** D-P0.15d-1 (derive the run's ACTIVE phase set by
     rigor so the loop skips opted-out phases), D-P0.15d-2 (`refundPhases` at the pod's reduced-commit/stop
     path), D-P0.15d-3 (the provisional-credit `renderCredits` at the live commit — record the `sdk_stream`
     row + `usage.tick` per phase).
   - **Unit-test** the loop over a `FakeEngine` + fake transport + PGlite: a multi-phase Review advances +
     commits each phase, opens the gate at `approve_scope`, resumes, and delivers; a `phase:"N"` run commits
     exactly phase N then stops; the oracle's incomplete→guided-retry path fires once; no secret leaks. (The
     G21 harness already composes api + worker + FakeEngine — extend it to drive the pod loop end-to-end.)
2. **A deployable worker.** Replace `apps/worker/Dockerfile` (the P0.01 sleeper) with a real multi-stage image
   mirroring `apps/api/Dockerfile` (build the `@rhema/worker` slice, `pnpm --prod deploy`, run
   `node dist/main.js`); add a `worker` step + image to `cloudbuild.yaml`. **Decide + implement the deploy
   topology** (the always-on worker consumes pg-boss + runs crons, so it cannot scale to zero): EITHER a Cloud
   Run service with `min-instances = 1` + CPU-always-allocated, OR a small GKE `Deployment` (1 replica) — bake
   it into `infra/pulumi/compute.ts` with the worker env (`DATABASE_URL`/system URL, `REDIS_URL`, the run-task
   image DIGEST, `KUBE_SERVICE_ACCOUNT=run-task-ksa`, `K8S_NAMESPACE=runs`, `INTERNAL_API_URL`, `PROXY_BASE_URL`,
   `OBJECTS_BUCKET`, the RS256 signing-key secret). Grant the worker's SA the roles it needs to launch GKE Jobs
   (`container.developer` / a scoped Job-create role) + read the secrets. `pulumi preview` clean; unit-test any
   pure config; the worker Dockerfile builds in `cloudbuild.yaml`.
3. **Confirm the api reachability + the run-token key.** The api Cloud Run service must run the real image
