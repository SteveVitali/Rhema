## Follow-on harness defects the live passes surfaced

Each verification dispatch peeled the next latent arm defect; all harness, product
correct every time.

- **F-R6FIX.45-6 — T14's quiet-hours check queried only the last 4h.** Tonight's leg ran
  ~9h after the armed window ended (16:29–19:29Z); zero in-window deliveries sat in the
  4h tail so `every recent run_finished row is undelayed` false-fired `armed nothing`.
  Witnesses existed and were correctly deferred (`16:41/17:41/17:54Z → visible_at
  19:29:0xZ` = the window end exactly). Fix: the witness query bounds to
  `created_at >= currentWindowStartUtc`; no in-window witness → honest "unexercisable"
  error, never `armed nothing`.
- **F-R6FIX.45-7 — T14's obligation arm could pick a finding whose obligation already
  carries an open decision row.** `createDecisionRequest` re-uses an obligation's open
  row rather than landing the swept `re-defer` row — iteration 1 deferred the root
  finding of the obligation the escalate arm's row sat on → sweep returned the
  obligation to open (`cause:horizon`, verified in `obligation_transitions`) and reused
  the `decide/dismiss` row → the `re-defer` waitFor timed out. Fix: candidates exclude
  root findings of obligations with open `decision_requests` (DB when bound; the
  escalate-selected DOM exclusion as the unbound fallback).
- **F-R6FIX.45-8 — the badge arm's un-escalated exclusion trusted `data-selected`.**
  `data-selected` marks only the finding's LATEST disposition kind — a finding escalated
  then re-disposed (or re-rendered post-obligation-transition) renders escalate
  un-selected, and re-escalating is an idempotent noop: 200, no new disposition, no new
  decision row, badge +0 (04:11:59 POST on `PXC4` proved it). Fix: when bound, exclude
  every finding that already has an `escalate` disposition — escalate is once-per-finding.
