## Goal

BL-93 (R5 B9, P2): Timeline renders runs as one long undifferentiated scroll —
shouty `'WHAT IT DELIVERED'` caps labels, failed runs dominate the view, approvals render
as plain text. Give the timeline visual structure: differentiate run states (failed vs
delivered vs in-flight get distinct, non-shouty treatments), soften the all-caps labels to
the design system's label style, and render approvals as structured items (kind, when,
actor — not a bare text line). Visual only: same data, same routes.

## Spec §§ / anchors

- The timeline/run-history surface under `apps/web/src/spa/` (the run-list + run-history
  render — `chrome-data.tsx`/`chrome.tsx` and the `?view=tree` history surface are the
  likely owners; confirm at read time via `data-*` names in `dom-contract.ts`).
- Reuse `ui-*` label/badge primitives from `packages/ui` for the state treatments; add a
  `data-run-state` (or extend the existing vocabulary) so legs can assert states.
- Approvals: they already carry kind/timestamps in the twin — render them as rows with a
  badge, not inline text.

## Acceptance (deterministic)

- DOM tests: delivered/failed/in-flight run rows carry distinguishable state treatments;
  no `WHAT IT DELIVERED`-style hard-caps strings remain (case-insensitive check); approval
  entries render as structured rows (assert a data-hook per kind).
- `pnpm turbo build lint typecheck` + web suite + `check:dom-contract`/`spa-budget`/`spa-env` green.
- Preview walk: a workspace with mixed run states screenshotted; preview destroyed per the
  owned lifecycle.
