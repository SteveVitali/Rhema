# 296_R6FIX.29 — BL-116: invite over-redemption race (capacity guard on the UPDATE)

**Status:** done (PR opened, unmerged — OPERATOR)
**Class:** run-time insert — defect fix, rh-low N-A1/RH-A1-2
**Base:** `main` @ `26ba5bae`
**Branch:** `stevevitali/r6fix-29-invite-race`

## Defect

`inviteGate.consume` guarded capacity in the INSERT's SELECT source (`cand.used_count <
max_uses`, evaluated at the statement snapshot), not on the UPDATE that mutates `used_count`.
Two concurrent consumes of a single-use code by **different** users each observed
`used_count=0 < 1` at their snapshots, both inserted into `invite_redemptions` (the
`(code, user_id)` unique index cannot fire across users), and `used_count` ended at 2 —
over-redemption past `max_uses`. The 0016 migration comment claims the last-use race is
closed by "a conditional UPDATE (used_count < max_uses in the WHERE)" — the code did not
deliver that: the predicate lived in `cand`, not the UPDATE.

## Fix

`apps/api/src/invite.ts` — invert the CTE so the seat claim IS the guarded UPDATE:

- `upd` updates `invites set used_count = used_count + 1` with all validity predicates in its
  WHERE, including `used_count < max_uses`. Concurrent claimants serialize on the row lock and
  Postgres re-evaluates the qual against the newest committed version (EPQ) — exactly one wins.
- `not exists (invite_redemptions for this user)` keeps an idempotent same-user re-consume
  seat-free (previously guaranteed by `ins` feeding `upd`; preserved explicitly).
- `ins` records the redemption only for a claim `upd` actually won (`from upd`), so a refused
  consume leaves no phantom redemption row.
- Documented residual: a *concurrent* same-user double-consume on a multi-use code can
  over-count `used_count` by one — fails closed (denies capacity, never over-grants).
