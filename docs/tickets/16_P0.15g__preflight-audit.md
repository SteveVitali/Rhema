## 3. The vendored-SDK question, answered explicitly (Stage 3)

**Is the SDK real + runnable in the image?** The wrapper is **real** (not type-defs): `sdk.mjs` is a 1.5 MB
minified ESM module with a working `query()` (`package.json:3-9` → `main: sdk.mjs`, `sdk-adapter.ts:56`
dynamic-imports it). But it is a **thin control-plane wrapper that spawns a separate compiled `claude` CLI as
a child process** and speaks a stdio control protocol to it.

### 3.1 The native `claude` binary is NOT vendored — the #1 blocker (F1)

- `sdk.mjs` spawns a subprocess: `child_process` + `spawn(` at `sdk.mjs:16,19,25,100,106`;
  `getDefaultExecutable(){return al()?"bun":"node"}` and a `spawnLocalProcess` (`sdk.mjs:90`).
- When `options.pathToClaudeCodeExecutable` is unset, it resolves the native binary from the platform
  packages: `sdk.mjs:100` — `let YE=u.pathToClaudeCodeExecutable; if(!YE){ … oo.resolve(Nc) …
  if(!ia)throw Error(\`Native CLI binary for ${process.platform}-${process.arch} not found. Reinstall
  @anthropic-ai/claude…\`)}`. The candidates it `require.resolve`s are `@anthropic-ai/claude-agent-sdk-<plat>/claude`
  (`package.json:59-68` `optionalDependencies`; `manifest.json` lists each platform's `claude` binary at
  **~216 MB** for linux-x64).
- **The image vendors only the wrapper.** `Dockerfile:75-83` copies `apps/run-task/vendor/` and, if
  `vendor/claude-agent-sdk` exists, installs **only that one package** as
  `node_modules/@anthropic-ai/claude-agent-sdk`. The platform packages are absent from the vendor tree
  (`find apps/run-task/vendor` shows no `claude`/`claude.exe`/`cli.js`), and the sandbox subnet has no egress
  to fetch them.
- **`pathToClaudeCodeExecutable` is never set** anywhere in our source (grep: only hit is the SDK's own
  `sdk.d.ts:1824`). `AgentSdkQueryOptions` (`options.ts:52-77`) has no such field, and `toSdkOptions`
  (`sdk-adapter.ts:25-27`) is the identity.

**Verdict:** the first live `query()` throws `Native CLI binary for linux-x64 not found` at the very start of
the phase — caught by the D-P0.15e-4 sink (`agent-entry.ts:200-210`) and surfaced as an `engine.error`, i.e.
this WOULD have been the next live surprise. **Confirmed fact, not hypothesis.** Fix: vendor the linux-x64
(musl if the base is Alpine — the base is `node:22-bookworm-slim`, so glibc `linux-x64`) `claude` binary into
the image and/or set `pathToClaudeCodeExecutable`. The binary is large (~216 MB) — budget image size + the
`vendor/README.md` operator step must be extended to include it.

### 3.2 Skill discovery is unwired (F2)

The prompt is `/editorial-review\n<key=value inputs>` (`options.ts:123-128`, `agent-sdk-engine.ts:59`). For the
CLI to resolve the `/editorial-review` skill it must be in a **discovered** location. The skill IS ported
(`packages/protocols/skills/editorial-review/SKILL.md`, valid `name`/`description` frontmatter) and baked at
`/app/skills` (`Dockerfile:69`). But:
- `skillsDir` is **not a real SDK Options field** (grep of `sdk.d.ts`: `skillsDir` = 0 hits; the SDK exposes
  `skills?: string[]` and `settingSources?`). `options.ts:105` passes `skillsDir` → the SDK ignores it.
- `CLAUDE_CONFIG_DIR` is `/config` (`k8s-launcher.ts:145`, `scrubbed-env.ts:46`), a fresh tmpfs into which the
  harness writes only `phase-spec.json` + `hook.sock` — **not** the skills.
- Nothing copies/symlinks `/app/skills` into a CLI-discoverable path, and neither `skills` nor
  `settingSources` is set.

**Verdict (high-confidence hypothesis):** the CLI will not find `/editorial-review`; the model runs with no
skill (or errors on the unknown command). Fix: stage the baked skills into the CLI's discovery path at harness
time (e.g. `$CLAUDE_CONFIG_DIR/skills/…` or `<cwd>/.claude/skills/…`) and/or pass the SDK's real skills option.

### 3.3 Does it need any binary/subprocess not present, beyond the CLI?

The CLI binary is the only hard external subprocess. MCP servers are optional (`mcpServers?` at `sdk.d.ts` is
unset by our options), so none are required. `util-linux` (`setpriv`/`unshare`/`mount`) + `tini` are installed
(`Dockerfile:43-44`). Node is present. So the **only missing runtime dependency is the native `claude`
binary** (F1) — but it is load-bearing: without it the SDK cannot run at all.

### 3.4 How the agent's SDK request authenticates to the proxy

It **doesn't, yet** — this is D-P0.15f-2 (K2). The agent env carries `ANTHROPIC_BASE_URL` = the egress-proxy
directly (`scrubbed-env.ts:44`, `k8s-launcher.ts:140`) and the scrubbed env **forbids** the proxy credential
(`scrubbed-env.ts:12-27`). So the CLI's request to the proxy carries no `x-rhema-proxy-credential` →
`prepareProxyRequest` returns 403 `egress.denied` (`handler.ts:151-157`). The intended path (harness-uid
injector stamping the header) has no live caller. Fix = P0.15g Stage A item 2.

## 5. The model-allowlist trap (F4) — detail

- `buildQueryOptions` sets **no top-level `model`** (`options.ts:98-120`), though the SDK supports it
  (`sdk.d.ts:58 Options.model?`). So the **main-context** model is whatever the vendored CLI (claudeCodeVersion
  2.1.259, `manifest.json:2`) defaults to.
- The proxy enforces the model on `body.model` with an **exact** `.includes()` (`credential.ts:96-98`) against
  `MODELS_BY_TIER` and then priceability (`handler.ts:199-206`). Balanced allowlist =
  `[claude-sonnet-5, claude-opus-5, claude-haiku-4-5]` (`allowlist.ts:13`); rate table ids are bare
  `claude-sonnet-5/opus-5/fable-5` (`packages/contracts/src/domain/rates.ts:40-47`).
- **Concrete mismatch already in the tree:** the `base`-tier research subagent model is
  `claude-haiku-4-5-20251001` (dated, `roster.ts:31`) but the `base` allowlist is `[claude-sonnet-5,
  claude-haiku-4-5]` (`allowlist.ts:12`) — a base-tier research fan-out would 403 (`model not on allowlist`). A
  mapper fixture uses the same dated id (`mapper/fixtures/index.ts:47`), suggesting real requests carry dated
  ids while the allowlist carries bare ids.
- **Risk:** if the CLI's default main model id is not EXACTLY on the run's allowlist (and priceable), the
  proxy 403s the very first inference. Fix: set an explicit, allowlisted, priceable `model`; align `roster.ts`
  ids with `MODELS_BY_TIER` (and the rate table) exactly. **This is a hypothesis on the CLI's default id** —
  but the base-research dated-id mismatch is a **confirmed** allowlist bug regardless.

## 6. The `/work` layout inconsistency (F3) — detail

Four places disagree on where a project's files live and where the agent runs:

1. **Materialize (what actually happens):** `materializeWork` writes each manifest entry at
   `workPath(workDir, entry.path)` = `/work/<entry.path>`, **ignoring `entry.root`**
   (`materialize-work.ts:42-46,73-77`). The seeded draft's `mirror_path` is `drafts/v1.md` with **no `project/`
   prefix** (`real-projects.ts:57`), and the mirror manifest carries that raw path (`materialize.ts:219`
   `path: b.path`). ⇒ **files land at `/work/drafts/v1.md`.**
2. **SDK/CLI cwd:** `runspec.ts:198` sets `request.cwd = "/work/project"` → `buildQueryOptions` →
   `options.cwd = /work/project` → the SDK spawns the `claude` CLI with cwd `/work/project`, **which does not
   exist** (ENOENT at CLI spawn), and relative reads resolve under the wrong root.
3. **Harness spawn cwd:** `harness-main.ts:121` uses `/work` (the P0.15f fix) and `mkdir`s it — so the
   agent-entry PROCESS runs in `/work`, but it hands the SDK `request.cwd=/work/project` (2).
4. **Hook boundary:** `compileSeatPolicy` defaults `roots.project = "/work/project"` (`seat-tables.ts:15,138`)
   and `runspec.ts` does **not** set `hookPolicyInput.roots`. SEAT_MOUNTS glob `drafts/**` root `project`
   (`seat-tables.ts:21`). The hook resolves an absolute read against `roots.project` (`paths.ts:89-92`): a read
   of `/work/drafts/v1.md` is **not within `/work/project`** ⇒ **DENY** ⇒ `boundary.attested violations ≠ 0`,
   failing the exit criterion even if the model reads the right bytes.

**The P0.15f "cwd=/work" spawn fix treated a symptom.** The real defect is `materializeWork` not honoring the
mount root; the hook table + runspec cwd + the `sdk-adapter`/`hook-daemon` tests all already assume
`/work/project`. **Recommended fix:** materialize project entries at `/work/${root}/${path}` (persona at
`/work/personas/…`), set `request.cwd`/spawn cwd to `/work/project`, keep hook roots default. Then all four
agree. (Note: `materialize-work.test.ts:44` already asserts `workPath("/work","project/draft.md")` — but real
entries lack the prefix, so the test's input is unrepresentative; add a test with the real `drafts/v1.md`
entry + `root:"project"`.)

## 7. Recommended sequencing — is P0.15g's scope sufficient?

**No — P0.15g Stage A must be extended with the NEW construction below before the next paid run.** As written,
Stage A closes K1 (caps), K2 (injector), K3 (retry) — necessary but not sufficient. Add to **Stage A (offline,
no spend, unit/Docker-testable):**

1. **F1 — vendor the native `claude` binary** into the run-task image (linux-x64 glibc) and/or set
   `pathToClaudeCodeExecutable`; extend `vendor/README.md` + a Docker/CI check that the binary resolves and
   `query()` can spawn it (a `--version`-style smoke, offline). *Highest priority — nothing runs without it.*
2. **F2 — wire skill discovery**: stage `/app/skills` into the CLI's discovery path (harness step) and/or pass
   the real SDK skills option; unit/Docker-test that `/editorial-review` resolves.
3. **F3 — reconcile the `/work` layout** (materialize under mount root + cwd `/work/project`); unit-test with
   the real seeded manifest entry, and assert the hook allows the draft read.
4. **F4 — set an explicit allowlisted+priceable main `model`** and align `roster.ts` ids with
   `MODELS_BY_TIER`/rate table exactly; unit-test that every roster + main model id is on the tier allowlist
   and priceable.
5. **F5 (RISK) / F6 (RISK)** — map or drop the ignored SDK option fields; add `+setgid` **and `+sys_chroot`**
   to the entrypoint ambient set (F6 rides with K1).

Only after 1–4 land offline does the run stand a chance of reaching the model on the first paid attempt; the
remaining live residue (K5 completion-oracle parsing, D-P0.06-1) is then the legitimate "first live SDK
exercise" the ticket describes. Keeping F1–F4 as "diagnose live" repeats the P0.15c→f pattern: each is a
distinct construction gap that a paid Stage B would surface one at a time.

**Bottom line:** treat F1, F2, F3 as BLOCKER Stage-A construction (peers of K1–K3), F4 as a strong RISK to fix
offline, and only then run Stage B.
