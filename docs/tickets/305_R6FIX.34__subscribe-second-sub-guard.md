# 305_R6FIX.34 — subscribe arm refuses a second subscription (BL-114)

**Status:** done (Stage A; PR opened, unmerged — OPERATOR)
**Class:** run-time insert — BL-114 money-integrity defect
**Base:** `main`
**Branch:** `stevenvitali/r6fix-34-subscribe-guard`

## Defect

`POST /billing/checkout` `kind=subscribe` never checked for an existing subscription. The
billing ladder's non-current tier cards still render `subscribeForm` for a subscribed user
(change-plan is fenced — `change_plan_unavailable` — until the D-R6FIX.5-1 price_ registry
lands), so that arm was the effective in-app switch path and could mint a **second concurrent
Stripe subscription** on one billing account instead of a plan switch. Recorded by
263_R6FIX.13 while fencing change-plan; out of that ticket's scope.

## Implementation

Inside the subscribe arm's tenant transaction, after the `purchase_closed` and
`stripe_unconfigured` refusals, a `subscriptions where billing_account_id = $1 and status in
('active','past_due')` probe (the read's own live-status set) refuses with
`{ error: "subscription_active" }` → 409 — before any checkout row or Stripe call. The web
half rides the existing code path: `ApiError.code` → `?notice=subscription_active` →
`billingNoticeFor` → new `subscriptionActiveNote` pointing at the billing portal. New refusal
state added to the §14.6 failure matrix with its test ref.

## Residual

Concurrent subscribe POSTs on a Free account can still each mint a session row (the guard's
probe runs inside each tx; the second sub only materializes if BOTH Stripe checkouts
complete). The webhook half is the stronger same-seam enforcement point — noted for the
D-R6FIX.5-1 design. The UI still renders the form (per BL-114's scope — the guard, not a
redesign); refused users land the truthful portal notice.
