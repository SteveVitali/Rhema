## Goal

The full §6.4 Approval surface in the IDE: every one of the twelve `GateKind`s renders as the same
approve-with-deadline card in the run card (Timeline, P1.05) and the Inbox/Needs-you row, with its
kind's structured fields editable where §6.4 item 4 makes them editable; the presence-timer UX
(REQ-SPEC-18) driven off the server-side deadline state that already exists; the per-project
approval-policy settings page (three values + per-kind deadline overrides + per-run override); the
standing-guidance management surface in settings (REQ-GATE-10); the permanent on-card decision
record (REQ-RUN-5/6); and the first-run inline explainers (§5.1 progressive disclosure). The
mechanics — deadlines, expiry job, conditional resolution, write-back overlays, guidance capture —
landed in P0.10 and PRB.05 and are **not** re-implemented here; this ticket owns rendering, editing,
and policy surfaces over them.

## In scope — deliverables

1. **All twelve kinds, one card.** Extend `buildGateCard`/the `GateCard` component so every
   `GateKind` — `confirm_cost`, `approve_plan`, `approve_scope` (informational `blocking:false`,
   blocking 2 h, and the spend-gate variant per REQ-SPEC-17), `approve_triage`, `approve_outline`,
   `approve_sample`, `approve_cutlist`, `choose_thesis`, `continue_rounds`, `spend_overrun`,
   `resume_partial`, `refusal` — renders the §6.4 anatomy: the artifact under decision, the deadline
   (relative **and** absolute) or "waiting for you", the do-nothing outcome in one sentence, cost so
   far + remaining estimate, and the actions **Approve** (pre-filled with the agent's
   recommendation — universal, one click) · **Approve and run autonomously** (secondary) ·
   **Edit guidance / Keep planning** · **Wait for me** (`hold`) · **Stop**. Kinds whose workflow
   does not exist yet (`approve_cutlist`, `choose_thesis`, `continue_rounds` — 1.x workflows) still
   render from a fixture so the component is complete, and the registry maps kind → body component.
2. **Structured-field editing (REQ-GATE-5/6).** The shared spine-and-sections field set — spine
   claims (reorder, strike, add with a note), section rows (order, target words, function), cut-list
   toggles (protect/restore), apparatus budget — as an editable view model over the artifact's
   sidecar rows; prose stays read-only. Edits post as `GateEdit{artifactVersionId, rows}` through
   the existing `resolveGate` → `serializeGateOverlay` path (a new user-authored artifact version +
   `Decision.overlayVersionIds`), and every change also lands as a `Guidance` record. The card
   history line reads "approved by you at 14:02 with 3 changes" (change count on the Decision). On
   **Confirm scope** the editable fields are stage, phase toggles, venue/audience corrections,
   concerns, scope narrowing — per REQ-SPEC-17's three variants. On **Approve triage** the
   PRB.05 ledger-as-disposition-UI stands (overrides write `actor: user` rows; bulk actions open one
   consolidated preview). The Approve-plan fields are exercised end-to-end only when P1.10's Draft
   produces a real `02-structure-plan`; here they are proven against the parsed plan fixture.
3. **Presence timer UX (REQ-SPEC-18, full).** A focused project tab on an auto-proceed gate shows
   the 10-minute "proceeding in 9:40 unless you say otherwise" countdown; `blur`/close reverts the
   card to its long deadline; activity pings while reading pause the countdown and extend the
   deadline +10 min capped at +24 h (server state already in `gate-expiry.ts` — the web client sends
   `present`/`reading`/`blur` on visibility/focus events via `recordGateActivity`). Wait-default
   kinds never show a presence timer; spend/refusal kinds never auto-proceed under any display
   (`NEVER_AUTOPROCEED_GATES` asserted at the view-model level too). Auto-proceed decisions render
   `by:'timeout'` with `presence:true` on the card record.
4. **Per-project approval policy UI.** Project settings gets the three policy values verbatim —
   *Named approvals* · *Wait for me at each* · *Run to completion* — with the consequences stated
   (Wait-for-me opens a card after every phase; Run-to-completion resolves named gates
   `by:'policy'` and still opens spend/refusal gates), plus the per-kind deadline-override editor
   bound to the `approvalOverrides` schema rules (lengthen, remove → wait, add ≥ 2 h to wait-default
   kinds; spend kinds not offered). Changing the policy must not alter an open card's deadline —
   assert the API leaves `deadline_at` alone (REQ-GATE-3). The run sheet's per-run `--wait`/`--auto`
   override is P1.06's surface; this ticket exposes the `autoProceedRun` flag the sheet posts.
5. **Standing-guidance management (REQ-GATE-10).** "…and remember this for this project" on any
   card writes `scope:'project'` guidance (`standingRule` path already in `resolveGate`). Settings →
   project lists standing notes (text, source, workflows narrowed to, created), with **Retire**
   (`active:false`, never deleted) and **Edit** (retire + replace); the run-sheet "3 standing notes
   apply ▸" disclosure lists them (the sheet's chrome is P1.06; this ticket provides the query +
   the disclosure's content contract).
6. **Decision record + first-run explainers.** Every resolved/skipped/expired gate renders its
   permanent `Decision` line on the round card — "approved by you at 14:02 with 3 changes" /
   "auto-continued at 14:32" / "skipped by your Run-to-completion policy" (REQ-RUN-5/6;
   `by:'policy'` rows REQ-DATA-36 writes are displayed, not re-created). The first Approval a user
   ever sees carries the one-time inline explainer (what it is, the do-nothing outcome, that a
   parked run spends nothing) — once per user, never a modal tour.
7. **Inbox/Needs-you integration.** The approval row component for the Needs-you group and the
   §5.11 Inbox contract: blocked-on-you first by soonest deadline, inline **Approve** opening the
   artifact in a side sheet, "waiting for you" rows, the badge counting only approvals + decisions.
   (The standalone `/app/inbox` page is P1.19; this ticket ships the row + side-sheet components it
   mounts.)
