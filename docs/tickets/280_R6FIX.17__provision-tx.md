# 280_R6FIX.17 — BL-115: `provisionPersonalAccount` is a check-then-write race with no atomicity

**Status:** open · **Phase:** post-handoff defect insert · **Prereqs:** merged `main` @ `3a840396` · **Size:** S · **Origin:** `docs/build/BACKLOG.csv` BL-115 (277_R6LOW.1 sweep): `provisionPersonalAccount` (`apps/api/src/signup.ts`) performs an unguarded pre-read followed by five independent `db.query` writes — `billing_accounts` insert, `provisionTrial` (trial_entitlement + `trial_state` update), `workspaces` insert, `workspace_members` insert, optional `is_test` flag — each over the pool. Two concurrent provisions of the same user (signup + Better Auth `onUserCreate`, or a double-submit) both pass the pre-read and insert **two** `billing_accounts` + two `kind='personal'` workspaces + two memberships; the session→principal `limit 1` personal-workspace join then forks. A mid-provision failure also leaves orphaned billing/trial rows. REQ-DATA-4-adjacent (account-row atomicity).

## Run

Ride the existing transaction seam — no new client plumbing, no schema change.

1. `apps/api/src/signup.ts` — `ProvisionOptions.txRunner` + `SignupPolicyDeps.txRunner` (optional; the live `SignupApiDeps` already carries the required field and `createSignupRoutes` already passes it). The provision body moves into one callback: `pg_advisory_xact_lock(hashtext($userId))` FIRST (serializes concurrent provisions per user — the loser blocks until the winner commits, then the in-tx re-check sees the winner's rows and returns them), then the existence re-check, then all four writes on the tx client. `opts.txRunner.run(workspaceId, provision)` with the tx keyed to the minted workspace id — the account tables (`billing_accounts`/`workspaces`) carry no RLS; `workspace_members`' `workspace_id` check matches the minted id. `provisionTrial` runs on `tx` — trial rows are inside the same atomic write set. The `is_test` flag + Showcase seed stay POST-commit (each carries its own tx; the seed must see committed rows).
2. `apps/api/src/server.ts` — Better Auth `onUserCreate` passes the existing `txRunner` variable (same seam `createShowcaseSeeder` already uses).
3. `apps/api/src/signup.test.ts` — three PGlite pins: sequential double-provision returns the same workspace + exactly one row each; the advisory lock is the FIRST statement on the tx, keyed on the user id, re-check ordered after it (the mechanism pin — `pg_advisory_xact_lock` is session-scoped so a same-wire concurrent re-acquire can't block on PGlite; the lock serializes across the pool's distinct connections in production); a mid-provision failure rolls back all four row types atomically.
