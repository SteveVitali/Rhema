## Goal

The `visualize` verb works end-to-end per §7.5: the honesty-first data-resolution step, spec
generation (Vega-Lite / Mermaid / table) with bounded retries, deterministic server-side rendering
to light+dark SVG (+ lazy PNG@2x) in `packages/figures` running in the worker, the figure card
with type chips and disclosures, iterate-as-versioning, and insert-as-proposal with figure-claims
integration into Review. Figures are first-class assets under `assets/figures/<figure-id>/` with
the full provenance/verification schema — the data-honesty rule (no model-memory numbers) is
enforced before any spec is written.

## In scope — Stage A (code + tests, PR-able)

1. **`packages/figures` — the renderer.** Vega-Lite spec → validated (schema check) → compiled →
   light + dark SVG themed from `packages/tokens` (one neutral palette, label contrast ≥4.5:1, no
   animation); Mermaid source → `beautiful-mermaid` → same light/dark pair; GFM/HTML tables pass
   through unrendered. Byte-identical output for identical input (fixed fonts, no timestamps, no
   random seeds — REQ-VIZ-6/7/8's determinism; the render runs in the worker via a `figure.render`
   job so a persisted render is never browser-only). PNG@2x lazily via `@resvg/resvg-js` on first
   export/display request. Determinism test: render the same fixture twice + in two environments,
   assert byte equality.
2. **The `FigureAsset` contract + asset store.** `packages/contracts/src/domain/` type over the
   `figures`/`figure_versions` tables: `alt` (required, ≤250 chars) + `sourceLine` (required before
   insert — REQ-VIZ-2), `specKind`, `provenance` (kind + refs + verification state), `caption`,
   versions. Storage writes the §7.5 directory layout under `assets/figures/<figure-id>/`; a
   figure not yet inserted lives in the project's working figures (REQ-VIZ-12).
3. **The `visualize` run + manifest.** `manifests/figure.ts` — the §6.2 row: data (judge — the
   honesty step, REQ-WF-14) → spec (generate — schema-validated, ≤3 retries with the validator's
   error fed back) → render (package — the deterministic render) → caption (generate — title/
   caption/alt/source line draft). No Approval — the preview-before-insert card is the consent
   (REQ-VIZ-16's cost honesty: first render 5–15 cr, iterations 2–8, chip edits 0 — the estimator
   `ESTIMATORS.figure` reflects this). Rhema-owned (no upstream pin) — declare in the port
   manifest like `research_burst`.
4. **Data-resolution honesty step (REQ-VIZ-4/5; REQ-WF-14).** The data phase classifies every
   row's origin against the six kinds; model-memory numbers are refused — the assistant says so
   and offers the path (point at a source, upload a CSV, type the values). If the user insists,
   the figure is created with `provenance.kind="none"` + a persistent `[unverified data]` badge
   that exports carry too. The data table renders in the card *before* the figure; user cell
   corrections write `user_typed` provenance rows.
5. **Entry points (REQ-VIZ-3).** All five wired to the same run: chat "make a chart of…" (the
   `visualize` tool's sheet → run), the selection popover's **Visualize** (provenance `selection`
   + anchor), `/visualize` with `@claim`/`@asset`/free text, **Edit figure** on an existing block
   (opens its card at the current version), the craft finding's **Visualize** action.
6. **The figure card.** Type chips (chart-kind switches that are local spec edits — 0 cr, no
   model call), caption/alt/source fields, Data / Spec / Versions disclosures, the insert-after
   anchor picker, the `[unverified data]` badge when `kind:"none"` or verification warrants.
7. **Iterate (REQ-VIZ-9).** Each iterate turn re-runs spec generation with the previous spec as
   input → `figure_versions` n+1 retaining the prior spec/data/provenance; the Versions strip
   shows thumbnails + the request text per version + one-click restore; a data change re-runs the
   honesty step, not just the spec.
8. **Insert-as-proposal (REQ-VIZ-10/11/12).** Insert renders a proposal card beside the Page at
   the stated anchor; Accept is one transaction writing the Rhema Markdown figure block
   (`![alt](asset://fig_<id>)`, caption + footnoted source line, `<!-- rhema:figure id=…
   version=n -->`); Reject keeps the asset in working figures. Figure numbers derive from document
   order at render/export time. Insert into a frozen vN rides the existing fork path (vN+1) and
   marks the figure's claims pending verification (§7.5's Review integration).
9. **Review integration (REQ-VIZ-13/14).** The figure's claims become Tier-1 review claims: the
   claim inventory consumes `provenance.json` + `data.csv` for inserted figures (the reviewer's
   input assembly mounts `assets/**` already — wire the figure's data into the inventory input);
   verification re-fetches and recomputes; the verdict writes back to `provenance.verification`
   and the badge follows (`verified`/`contradicted`/`unverifiable`); a figure with
   `kind:"none"` is `Unsupported` by construction. The claims table (P1.07's dossier surface)
   groups figure claims under their figure number.
10. **Export path (REQ-VIZ-15 — the asset half).** The asset packages per-format correctly for
    P1.18 to consume: light SVG (never dark in exports), PNG@2x where the format needs raster,
    native table for md/docx, alt text + source footnote always; `[unverified data]` adds a
    caption note. (The export formats themselves are P1.18.)

## Cross-cutting invariants — re-check before opening the PR

- The data-honesty rule is load-bearing: no figure ships numbers the model remembered; provenance
  is structured data, not a caption convention (REQ-WF-14).
- Persisted renders are server-side only — the browser never produces the canonical SVG
  (REQ-VIZ-7).
- Figure insertion rides the proposal/fork machinery — never a direct write into a frozen draft
  (REQ-DATA-24's invariant preserved).
- Canonical vocabulary; `figure.render` is a worker job, not a run phase name shown to users.
