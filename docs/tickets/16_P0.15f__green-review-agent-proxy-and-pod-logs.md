## State carried in from P0.15e (proven LIVE 2026-09-04 — do NOT redo)
- **The pod→server commit/deliver loop RUNS LIVE.** The harness reads the run token (0400 Secret, `fsGroup`
  fix), heartbeats `provisioning→running`, fetches the server-authored run spec over the wire
  (`GET /internal/runs/:id/runspec`), materializes `/work`, and launches the agent. D-P0.15d-4's machinery is
  validated to the agent-execution boundary. The loop + delivery are unit + integration-tested through the real
  api routes + PGlite (`integration/src/pod-loop.test.ts`).
- **~10 live-only deploy bugs are fixed** (committed in P0.15e, PR #21): the per-run Secret `fsGroup`/`0440`;
  the commit-loop heartbeat; the proxy COS startup (AR `docker login` + `DOCKER_CONFIG` on tmpfs + `-p` vs
  `--network host`); the proxy secret full-resource-name; the egress-proxy SA `artifactregistry.reader`; the
  `run.app` PGA DNS zone + the proxy-tier ingress firewall (both in `network.ts`). A plain `pulumi up` now
  includes the DNS + firewall fixes.
- **The egress-proxy comes up + is reachable + healthy.** A sandbox pod probe reached it and got a correct
  `403` (no credential); the MIG health check passes. `ANTHROPIC_BASE_URL` is **`http://`** (the proxy serves
  HTTP; proxy→Anthropic is HTTPS).
- **The blockers this ticket closes** (captured as `DEFERRALS.md` **D-P0.15e-2/3/4**):
  1. **The live agent SDK call never reaches the proxy** (the load-bearing green-Review blocker,
     **D-P0.15e-2**). With the proxy healthy + reachable, a real run's agent (uid `agent`) makes NO request to
     the proxy — so no inference, no commit, no delivery, `$0` metered. Likely the vendored-SDK/`AgentSdkEngine`
     first live exercise hanging before the call (**D-P0.06-1/4**) OR the proxy's response-BUFFERING is
     incompatible with the SDK's streaming (**D-P0.07-5**; `apps/egress-proxy/src/server.ts` `undiciForwarder`
     buffers the whole response before returning).
  2. **Pod logs are unreachable** (**D-P0.15e-4**). `kubectl logs`/`exec` fail with konnectivity
     **"No agent available"**; Cloud Logging is empty for long-running run-task pods — so #1 could not be
     diagnosed live.
  3. **The Cloud Run worker cannot launch GKE Jobs** (**D-P0.15e-3**). `@kubernetes/client-node`
     `loadFromDefault()` finds no kubeconfig on Cloud Run; P0.15e ran the worker out-of-band to validate the
     launch path.

## In scope — Stage A (offline, no spend; ends in a reviewable PR; one implement-spec session)
1. **Readable agent-error observability (the diagnosis enabler; part of D-P0.15e-4/D-P0.06-1).** The pod must be
   debuggable even when konnectivity is down. Have `agent-entry` capture a thrown SDK/engine error (not just the
   success result) into `.rhema/agent-result.json` (or a sibling), and have the harness loop READ it and report
   it — as a run event and on the `failStep` reason — so an agent hang/crash surfaces in `run_events`/`steps`
   (queryable from the DB) without pod exec. Unit-test the harness path: an agent-error file → a `run.error`/
   step-fail event with the message; a missing file after the agent exits → the existing `artifact_missing`
   incomplete verdict.
2. **The worker GKE-Job launcher without out-of-band (D-P0.15e-3).** Pick + implement ONE: (a) move the worker
   to a small in-cluster GKE `Deployment` (1 replica; in-cluster SA → `loadFromDefault` works; drop the Cloud
   Run worker service), OR (b) build the launcher's `KubeConfig` explicitly from the GKE endpoint + CA + the SA
   metadata OAuth token (so the Cloud Run worker can create Jobs). Keep it a thin, unit-testable seam;
   `pulumi preview` clean; note the choice + rationale.
3. **The proxy SSE/streaming pass (D-P0.07-5), IF diagnosis points there.** If the agent SDK streams
   (`stream:true`) and `undiciForwarder`'s whole-response buffering is the hang, make the proxy stream the
   response through (pass-through body) while still metering usage + logging server-tool fetches from the SSE
   frames (extend `extractResponseServerToolsSse`). Unit-test with a recorded SSE fixture: `fetch`/`search`
   rows emitted once, usage folded, the stream delivered incrementally. (This may be deferred to Stage-B
   findings if diagnosis shows the hang is pre-SDK instead — record which.)
4. **Konnectivity / pod-log egress (D-P0.15e-4), IF it is an IaC gap.** If `kubectl logs`/`exec` fail because
   the sandbox nodes cannot reach the konnectivity server / metadata path, bake the needed egress
   (firewall/route) into `infra/pulumi/network.ts` (the sandbox NODE tier only — pods stay locked by the
   NetworkPolicy). `pulumi preview` clean. If it is a cluster-config/ops issue rather than IaC, record it and
   rely on the Stage-A error sink (item 1) instead.
