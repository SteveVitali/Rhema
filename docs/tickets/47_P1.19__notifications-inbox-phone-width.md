## In scope — Stage A (code + tests, $0)
1. **The in-app notification channel.** A `notifications` store + delivery path fed by the same
   event stream the mailer consumes; the full §5.11 in-app column per event type (approval
   waiting; approval about to auto-proceed — T−10 min plus the 1 h reminder; spend gate; run
   finished; run failed/cancelled/recovered; auto-proceeded decisions with the decision and its
   cost; voice stale; credits 50/80/100%; trial ending day-12 + payment failed; chat reply while
   backgrounded; the off-by-default Advanced rows — finding streamed / phase finished — as a
   per-project opt-in; product updates stay email-only and off by default). **One notification per
   event per channel; every row deep-links per §4.2 shapes; a run's notifications collapse into
   one Inbox item that updates in place (collapse key = run id); OS-level notifications only when
   the project is not focused.**
2. **The Inbox at `/app/inbox`** (REQ-IDE-2 amended, REQ-IDE-48): the cross-project attention list
   using the same row component as the Needs-you group; inline **Approve** (opens the artifact in
   a side sheet so the user reads before approving) and **Read**; **one ordering, one badge
   rule** — rows sort blocked-on-you first (approvals and decisions by soonest deadline), then
   unread finished runs, then stale voices; the Rail badge counts **only approvals and decisions**,
   never finished runs or stale voices. Read state is server-side and shared — the 1.x app reads
   the same rows (REQ-MOBILE-19).
3. **Decisions inbox rows** (REQ-OBJ-5/6): `decision_requests` render as Decisions with
   "decide / dismiss" — standing escalations from response letters, escalated obligations,
   horizon-expired deferrals ("Deferred in round 1, horizon reached: decide / re-defer / drop"),
   and the §6.8 stall escalation firing for hand-run rounds too. Re-defer and drop are real
   obligation transitions (P0.12's ops — call them, don't re-implement).
4. **Returning to a finished run** (REQ-IDE-48): opening a project with an unread finished run
   lands on the walkthrough card with the deliverable on the Page — the letter for reviews,
   "what changed" for revisions, v1 for drafts.
5. **Quiet hours + preferences:** the existing `quietHours` schema wired through the in-app
   channel — quiet hours (default off) defer run-finished and chat notifications and **never
   approvals or spend gates**; preferences are per event type, server-side, shared by web and the
   future app; the two non-configurable rows (spend gate; trial-ending/payment-failed) cannot be
   disabled via API (REQ-ACCT-1 — the Settings UI is P1.20's; this ticket owns the enforcement +
   the prefs the UI edits).
6. **The phone-width web** (REQ-MOBILE-3 amended; REQ-SPEC-20 full-IDE form): below ~768 px every
   IDE route renders the reader-only Page **plus** the §10.1 input set — the gate card's
   Approve / Wait for me / Stop with its estimate block; the five dispositions with a note
   (Adapt edits the proposal in a sheet; Rebut and Escalate require a note; Defer pre-fills "Not
   this round"; dispositions reversible until the triage ledger freezes); chat — text only, no
   promote, the estimate chip before any research burst. **Never on phone-width:** run-start,
   run configuration, rigor/model/voice building, ingestion, diffs, billing, export, new project,
   bulk accept/apply, approval-field editing (§10.1's ✗ column verbatim). Consume the same
   `findings-core` + gate contracts the app will — no parallel implementation. The intermediate
   breakpoints per §5.1 (<1280 Margin ticks + Timeline overlay; <1024 single-column + Timeline
   sheet). The "Open in the Rhema app" banner renders only behind a shipped-app flag — never at
   MVP. Usage glance levels 0–1 render read-only at phone width (REQ-BILL-12's web half; the read
   models are P1.16's).
7. **Email matrix completion:** the §5.11 rows PRB.09 deferred — voice-stale weekly digest,
   trial-ending day-12, payment-failed (wired to P1.16's billing events), the optional hourly
   run-finished digest, product updates (off by default) — as worker jobs + prefs rows on the
   existing mailer; the signed one-click *Wait for me* / *Open* discipline is unchanged (never
   Approve — REQ-MOBILE-10's rule on email).
8. Deterministic verification: `turbo build lint typecheck` + `pnpm test` green; matrix fixtures
   per event row; breakpoint behavior tested at the layout seams.

## Cross-cutting invariants — re-check before opening the PR
- Approve is never a remote one-click action — signed email/notification actions are Wait-for-me
  and Open only (REQ-SPEC-1; REQ-MOBILE-10).
- Notification payloads carry ids + templated strings, never finding or draft text
  (REQ-MOBILE-20's rule applied to the in-app/push-prep payloads too).
- Spend gates never auto-proceed and never lose their notification (REQ-SPEC-1).

## Notes
The in-app channel and the email channel read the same event stream and the same server-side
prefs — build the in-app column beside PRB.09's mailer, not a parallel notification system. The
phone-width surface is deliberately contract-shaped: everything it renders is a `findings-core`
or gate payload the 1.x app will consume unchanged, so no phone-only abstractions.
