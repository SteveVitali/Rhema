## Goal
At build time, project the sanitized corpus and its validated sidecars into the exact DTO snapshots
the demo data source serves for the **document side** of each essay: editor docs per version, the
version rail, version diffs, what-changed, the files tree and the raw artifact pages. Each artifact
gets its own lazily loaded chunk; nothing is bundled or fetched at runtime. A contract/drift harness
proves every snapshot satisfies the real DTO types and equals a fresh projection; 218a plugs its
snapshot kinds into the same harness.

## In scope — deliverables
1. **Projector core** `packages/demo-corpus/src/project/*` (pure; the build script owns I/O): for
   each essay, one snapshot per document-side R3 §1 snapshot-backed method and key.
   - Version rail and editor docs per version follow the 214 version metadata, including Published
     (origin `imported`, "Published · sjsebastian.substack.com · fetched YYYY-MM-DD") and the
     "Writer-directed edit (not reviewed)" versions (REQ-CORPUS-12, REQ-CORPUS-13).
   - Version diffs keyed `n:m`; what-changed from 217's artifact.
   - Files tree (with the "working fragments not shown" note) and artifact pages for every
     `RAW_ONLY` artifact and source note as raw markdown (REQ-CONV-13).
   - *(REQ-CORPUS-12, REQ-CORPUS-13, REQ-CONV-13; the REQ-DWEB-3 data half)*
2. **Lazy chunking and the per-essay index** (REQ-CORPUS-9): one file per artifact, draft and source
   note, plus a small per-essay index whose schema 218a extends with its kinds. A test asserts no
   single snapshot exceeds the size of the one artifact it carries plus its declared envelope.
   Source notes load on demand from the index.
3. **Essay keys only.** Snapshots are keyed by corpus essay key. The `demo~<essay>` slug registry
   and its mapping are 220's (REQ-DWEB-1); the projector never mints slugs.
4. **Import-rule labels and raw markers** carried into every document-side DTO field that displays
   a converter-assigned value (REQ-CONV-14), and excluded-file references carried as "not
   published" markers (REQ-CORPUS-4, data half). Role vocabulary in any generated label follows
   S-10.
5. **The contract/drift harness** (owned here; 218a registers its kinds into it):
   - compile-time: typed loaders with `satisfies` against `@rhema/api-client` types;
   - runtime: a structural validator per snapshot kind, with a registration seam so 218a adds the
     dossier/run-report/timeline/figure/card kinds without forking the harness;
   - a drift test that fails when committed snapshots differ from a fresh projection.
6. **Synthetic snapshots** for this ticket's kinds, committed under the 214 layout beside the
   fixture, and the single regeneration command (corpus → convert → project) that 218a extends and
   219 reuses for real data.
