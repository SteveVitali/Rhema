## Goal
Add the **one** sanctioned demo write (ADR-126; GD-DEMO-METRICS-CARVE.R7) and nothing more:
- three anonymous funnel events written to a new append-only `demo_events` table;
- written only through a `SECURITY DEFINER` insert function owned by a new `NOLOGIN` insert-only
  role, with no IP, cookie, user id or UA, and a bounded abuse surface;

  does not pause on a `role_change`.

Separately, prove that every reused-surface client analytics event is suppressed in demo mode,
so a signed-in visitor's demo visit never enters a cohort read.

## In scope — deliverables
1. **The migration** `00NN_demo_events.sql`, additive only and lint-clean *(REQ-TOUR-9)*.
   - A new append-only table `demo_events(id, at, event, essay, step, src)`. `event` has a
     strict `CHECK` over `{demo.hub_viewed, demo.tour_started, demo.tour_completed_or_cta}`.
     This is a **new table, not a widened `CHECK`**. `essay`, `step` and `src` are
     length/range-bounded. No IP, IP-hash, user, cookie or UA column. Ids need no sequence grant
     (e.g. an identity or caller-supplied text id), or that grant is explicit and carries `ON`.
   - A dedicated **insert-only** role `rhema_demo_writer` (name owned here), created `NOLOGIN
     NOBYPASSRLS NOSUPERUSER NOCREATEDB NOCREATEROLE` in the same file (the 0045 `do $$ … $$`
     idempotent form), with `GRANT INSERT ON demo_events TO rhema_demo_writer` only.
   - **The channel** (P4-2): a `SECURITY DEFINER` function, e.g.
     `public.rhema_demo_event_insert(p_event text, p_essay text, p_step int, p_src text) returns
     void`, `set search_path = ''`, whose body is exactly one schema-qualified `INSERT INTO
     public.demo_events …`. It is owned by the new role (`ALTER FUNCTION … OWNER TO
     rhema_demo_writer`), so it executes with that role's INSERT-only privilege. Then
     `REVOKE ALL ON FUNCTION … FROM PUBLIC` and `GRANT EXECUTE ON FUNCTION … TO rhema_app` (the
     existing user-serving group role).
   - **No** `GRANT rhema_demo_writer TO <existing role>`, no `SET ROLE` anywhere, no `ALTER ROLE`,
     no `ALTER DEFAULT PRIVILEGES`, no `DROP`. The user-serving role gets no `SELECT`, `UPDATE`,
     `DELETE` or `INSERT` on the table — only `EXECUTE` on the function.
   - **The lint rule it satisfies** (stated in the migration's header comment and the PR):
     `check-additive-migrations` role-change rule (ADR-018 §8) — `CREATE ROLE … NOLOGIN` is
     additive; every `GRANT`/`REVOKE` in the file carries `ON <object>` (a privilege grant, not a
     role-membership change), so the "GRANT <role> TO <role> on a role not created in the same
     file" violation cannot fire; `ALTER FUNCTION … OWNER TO` is not an `ALTER ROLE/USER`.
   - A Drizzle parity entry is added if the package convention requires it.
2. **The RLS catalogue pin.**
   - `demo_events` is added to `rls-catalog.test.ts` as a non-tenant `system` store.
   - Its `USER_ROLE_GRANTS` entry proves the user-serving role holds no table privilege on it.
   - `tools/system-pool-boundary.json` is untouched: this write is not an elevated pool.
   - *(REQ-TOUR-9; spec §8.1)*
3. **The api route `POST /analytics/demo`**, mounted pre-auth like `/analytics/landing` on the
   same user-serving `deps.db`.
   - It validates the body against the enum, with payload ≤ 256 B.
   - It calls `select public.rhema_demo_event_insert($1,$2,$3,$4)`; there is no `SET ROLE` and no
     direct table `INSERT` in api code.
   - It never reads `x-forwarded-for`, a cookie or a session, and never sets a cookie.
   - It always returns 204; failures are dropped silently.
   - *(REQ-TOUR-9)*
4. **The web relay `POST /a/demo`.** It sits outside 220's demo guard, which covers `/p` and
   `/bff/p`.
   - Accepts `sendBeacon` `text/plain` JSON of ≤ 256 B.
   - An in-memory per-instance token bucket (e.g. 60/min per edge connection), never persisted
     and never keyed on a stored IP.
   - Forwards to the api with `cookie` and `authorization` **stripped**, so signed-in visitors
     stay anonymous.
   - Returns 204 always, with no `Set-Cookie`.
   - The forward follows the `recordLandingEvent` seam on the outer DataSource.
     `demoDataSource` stays write-free.
   - *(REQ-TOUR-9)*
5. **The client emitter.** One `emitDemoEvent(event, {essay, step?, src?})`.
   - Wired to the hub view (221a) and to the tour's start and completion-or-CTA callbacks (222).
   - It uses `sendBeacon` only, and is never armed off the demo boot.
   - `src` comes from the URL's `?src=`. The D-legs navigate with `?src=jrn` (cohort hygiene,
     R4 §6).
   - Extend `D3.readonly` (owner 221) to assert that `POST /a/demo` is the **only** non-GET and
     matches the event shape. The leg stays held `ready-to-flip`; it passes locally.
   - *(REQ-TOUR-9; REQ-DACC-3 restated)*
6. **Registration.**
   - The three `demo.*` events enter `ANALYTICS_EVENTS` and are classified in `emission-audit.ts`

   - Their envelope differs from the user/workspace envelope. How the catalogue represents an

   - *(REQ-TOUR-9)*
7. **The never-cookies and no-PII proof.**
   - A response-header test on `/a/demo` and `/analytics/demo`: no `Set-Cookie`, signed in or

   - A test that the route never reads `x-forwarded-for` or the UA.
   - A schema test that no PII column exists.

8. **REQ-DOPS-5: the catalogue-driven suppression contract.**

   - *(REQ-DOPS-5)*

## Notes
- **Decisions this ticket owns:**
  - the `demo_events` schema, the insert-only role's name, and the `SECURITY DEFINER` insert
    function (name, signature, grants);
  - the bucket parameters;
  - the anonymous-event representation in the catalogue;
  - the single suppression seam.
- **Why not role membership (P4-2).** `SET LOCAL ROLE rhema_demo_writer` from the api would need
  `GRANT rhema_demo_writer TO rhema_app`; the lint keys on the **grantee** being new, so that is a
  `role_change` and would PAUSE 224 Part B under `GD-DEPLOY.R7`'s additive condition. The
  definer-function channel needs no membership grant.
- **Ownership-assignment risk (re-confirm at build time).** On Cloud SQL PG16 the migration role is
  not a true superuser, and `ALTER FUNCTION … OWNER TO` requires it to be able to `SET ROLE` to
  the new owner. PGlite runs as superuser and hides this. Re-confirm the prod migration role's
  rights against the role it creates in the same file (PG16 `createrole_self_grant` / the creator's
  implicit grant). 224's preview migrate job is the first real proof (`D-R7DEM.6b-1`).
- **Pause rule.** If no design that meets REQ-TOUR-9 passes the additive lint and applies under
  the real migration role (e.g. it needs `ALTER ROLE`, a LOGIN role, or a `GRANT <role> TO
  <existing role>`), **PAUSE** for an operator ruling before 224. Never weaken the lint, and never
  route the write through the system pool.
