## Defect (verified at 277_R6LOW.1; BL-119)

`packages/db/src/migrate.ts` ran every statement through a `MigrationDb` that callers backed
with `pg.Pool` — `exec`, `_migrations` reads/writes could each land on a different connection.
There was no serialization between concurrent migrators (two deploy replicas racing the run),
and a migration file and its `_migrations` bookkeeping insert were separate statements: a crash
mid-run left applied-but-unrecorded DDL, and a mid-file crash left a half-applied file.

## Change

- `applyMigrations(db)` now requires a **pinned single connection** and documents it: one
  `select pg_advisory_lock(hashtext('rhema-db-migrations'))` wraps the entire run (session-level,
  since the run spans many per-file transactions — a tx lock would not), released in `finally`
  via `pg_advisory_unlock`. The `_migrations` create/read/write, each file's `exec`, and the
  unlock all ride that one connection.
- Each transactional migration file runs `begin` → `exec(file)` → `insert _migrations` →
  `commit`; any error rolls the file **and** its record back together — no applied-but-unrecorded
  drift, no half-applied file.
- Explicit escape hatch: a file whose first line is `-- no-migration-tx` runs outside the tx
  wrapper (for future transaction-forbidden DDL — e.g. `CREATE INDEX CONCURRENTLY`). None of the
  63 current files carry or need it; all 63 were swept for embedded `begin`/`commit`/`concurrently`
  /`create extension`/`alter type … add value` patterns — clean.
- New `applyMigrationsPinned(pool, opts)` (+ `MigrationPool`) exported from `@rhema/db`:
  `pool.connect()` checks out one `PoolClient`, adapts it to `MigrationDb`, runs
  `applyMigrations`, and releases it — every statement on the pinned connection.
- Pool callers migrated: `apps/worker/src/migrate.ts` (both the boot migrate and the preview
  invite migrate leg), `integration/src/live-prod-bringup.ts`, `integration/src/live-migrate-seed.ts`,
  `integration/src/server-postgres.test.ts`. Idempotent seed calls keep the pool-level `MigrationDb`
  (out of the row's scope — not part of migration bookkeeping). PGlite test harnesses
  (`orchestrator/src/testing/pg.ts`, `benchmark`/`mirror` harnesses, `db/src/testing/pglite.ts`)
  stay on `applyMigrations` — already single-connection by construction.

## Tests (packages/db/src/migrate.test.ts — 3 new pins, 8/8)

- Lock/order: `pg_advisory_lock` is the first statement, `pg_advisory_unlock` the last; the file's
  `begin`/`insert _migrations`/`commit` sequence rides inside.
- Atomicity: injected mid-file crash (probe DDL applied inside the file's tx, then throw) —
  `to_regclass` shows the probe rolled back, `_migrations` has no row for the file, and the clean
  re-run applies it. No drift.
- `applyMigrationsPinned`: a fake pool's single `conn` sees lock → begin → file → record → commit →
  unlock in order, and `release()` ran.
